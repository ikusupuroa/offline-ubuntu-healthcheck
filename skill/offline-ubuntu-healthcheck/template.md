# 輸出範本（template.md）

版本：0.6.4（2026-11-20，搭配 SKILL.md 0.6.4 與 report-template.html）

本檔只規定**回覆長什麼樣子**；怎麼判斷、什麼話不能說，看 `SKILL.md`。兩者看起來衝突時，判斷內容以 `SKILL.md` 為準；但下面這幾件事以本檔為準，因為它們是為了每次輸出一致而定的固定規則：整體風險的高中低、各輪的結論狀態與期限、處理清單的列數與順序、建議做法與指令的寫法、攻擊路徑的列法、問卷的題目選法。

## 共通規則（三輪都適用）

1. **先判斷這是第幾輪**（見下表），只輸出那一輪的範本。範本外層的四個反引號和 `markdown` 字樣只是示範用的框，輸出時不要包含。
2. **用繁體中文**，寫給機關主管和資訊人員都看得懂的語氣。
3. **標題逐字照抄**，包括編號。不增加、不刪除、不改名、不調換順序。範本外的段落一律不加（例如「關鍵提醒」「主機比較」）。
4. **〔 〕是要填的地方**，填完後〔 〕符號本身不要留下。沒有〔 〕的句子是**固定句**，逐字照抄。
5. **表格欄位逐字照抄**，欄數不變。某一格沒有資料寫「—」，不留白；整節沒有資料時，寫該節指定的固定句，標題仍然保留。
6. **主機依 H01、H02、H03… 的順序**。標「每台主機重複」的區塊，依序對每台主機各寫一次。
7. **數字照抄欄位**。可以數清單有幾筆（例如 `crit_high_fixes` 有幾筆、「其餘 3 則」），但不可以把不同主機或不同欄位的數字相加。每個數字都帶單位：`patches.unit` 是「則安全公告」就寫「則」，是「個套件」就寫「個套件」；0 也照寫，例如「0 則」。
8. **指令只用範本指定的來源**：公告的 `sudo pro fix` 指令取自 `crit_high_fixes[].commands`；安裝免費修補固定用 `sudo apt update`、`sudo apt upgrade`。第 1、2 輪放在 `bash` 程式碼區塊，一行一個指令；第 3 輪的追蹤表放在表格裡，用行內程式碼，多個指令用「；」分隔。
9. **只用標題、文字、條列、Markdown 表格與程式碼區塊**。不畫圖表，不做數字卡片。例外只有兩個：問卷一定要畫勾選表單（第 1 輪第 8 節、第 2 輪第 5 節），第 3 輪的主管報告檔由 `report-template.html` 產生。
10. **粗體標籤的冒號放在粗體外面**，寫成「**標籤**：內容」，不要寫成「**標籤：**內容」（後者在很多平台會直接顯示星號）。
11. **期限只用對照表裡的寫法**。基本的三種是「7 天內」「下一個維護窗口（最長 30 天）」「30 天內決定」；對照表另有幾種組合寫法，照抄。期限由短到長的順序是：7 天內 → 下一個維護窗口（最長 30 天）→ 30 天內決定；組合寫法裡只要含「7 天內」就算 7 天內，「〔日期〕前」不參與比較。
12. **結尾不另外列「如果你願意，我可以……」這類後續選項**。每一輪最後一節已經寫好下一步，照範本寫就好。
13. **公告編號的排序**：先比 cvss_max（由高到低），同分時比公告編號的數字，由小到大（例：同為 9.8 時，USN-5051-1 排在 USN-5288-1 前面）。「其餘 N 則」也照這個順序。
14. **問卷選項逐字照抄** SKILL.md「補問怎麼出」列的選項，不增不減。
15. 使用者問的事不屬於三輪中的任何一輪（例如單獨問某個套件、只想先修重大與高風險），就直接回答，不套範本，但仍要遵守 `SKILL.md` 的規則。

### 判斷是第幾輪

| 使用者這次 | 輸出 |
|---|---|
| 上傳 `findings-ai.json`（或 `findings.json`），要求分析 | 第 1 輪。之後又上傳另一份健檢檔（例如修補後重測），也當成新的第 1 輪，不和前一份比較 |
| 回答第 1 輪的問卷（勾選、編號或文字都算），或修改主機情境 | 第 2 輪（完整輸出） |
| 只回答第 2 輪第 5 節的補問 | 第 2 輪，但只輸出內容有改變的節（通常是第 0、4、5 節）；其他節寫「同上一次第 2 輪」，標題照留 |
| 說「整理成定稿」「給主管的版本」「正式報告」之類 | 第 3 輪（還沒做過第 2 輪也照做，用途與使用情境欄寫「未提供」） |

### 第 1 輪的固定判定

**整體風險**（依序判斷，符合就停）：

1. 任何一台主機有「網路」或「相鄰網路」途徑的重大或高風險公告、有嚴重度為「高」的 D 類發現，或 `support_status` 為 esm、legacy、eol、nonlts → **高**
2. 任何一台主機有重大或高風險公告，或有嚴重度為「高」的發現 → **中**
3. 其他 → **低**

**結論狀態與期限**：

| 類型 | 結論狀態 | 建議期限 |
|---|---|---|
| 自動更新 | 需立即處理 | 7 天內 |
| 免費修補 | 需排程處理 | 網路途徑的重大與高風險公告 7 天內；其餘下一個維護窗口（最長 30 天） |
| 訂閱 Pro | 需排程處理 | 30 天內決定；網路途徑的重大與高風險公告 7 天內（需先取得 Ubuntu Pro） |
| 重開機 | 需排程處理 | 下一個維護窗口（最長 30 天） |
| 其他設定 | 這一列涵蓋的發現中，任一項嚴重度為「高」：需立即處理；其他：需補問後判定 | 同左，「高」：7 天內；其他：下一個維護窗口（最長 30 天） |
| 稽核 | 需補問後判定 | 30 天內決定 |
| 其他 | 需補問後判定 | 30 天內決定 |

## 第 2 輪：情境判讀

### 第 2 輪的固定判定

**每台主機先分成三種情境**（依序判斷，符合就停）：

1. **暴露高**：可達性為「公開網際網路」，或重要性為「重要服務／敏感或個人資料」。但用途為「主機在但服務已停用」的主機不算暴露高。
2. **隔離**：可達性為「完全隔離」或「只限管理網段」。
3. **一般**：其他情況，包括「透過 VPN」「內網（一般使用者網段）」「不確定」與未回答。

**處理清單一台主機一列**：第 1 輪合成一列的項目，第 2 輪拆成每台主機各一列，編號寫成「P2-H01」這種格式（只有一台主機的項目照寫「P3」）。每一列依該台主機的情境，用下表判定結論狀態與期限。同一類型有多個條件時，**由上往下，符合第一個就停**。

「有網路途徑的入口公告」的意思：免費修補那幾列只看這台主機 needs_pro 為 false、attack_vector 為「網路」或「相鄰網路」的重大或高風險公告；訂閱 Pro 那幾列只看 needs_pro 為 true 的。

下表有三處刻意比 SKILL.md 的結論狀態定義更具體，以本表為準：可達性為「不確定」或未回答時，免費修補、訂閱 Pro、重開機仍判「需排程處理」；用途為「不確定」的主機仍可能是暴露高；本表不會產生「不在本工具範圍」。

| 類型 | 條件 | 結論狀態 | 建議期限 |
|---|---|---|---|
| 自動更新 | 不受情境影響 | 需立即處理 | 7 天內 |
| 免費修補 | 暴露高，而且有網路途徑的入口公告 | 需立即處理 | 7 天內 |
| 免費修補 | 隔離 | 需排程處理 | 下一個維護窗口（最長 30 天） |
| 免費修補 | 其他 | 需排程處理 | 網路途徑的重大與高風險公告 7 天內；其餘下一個維護窗口（最長 30 天） |
| 訂閱 Pro | 暴露高，而且有網路途徑的入口公告 | 需立即處理 | 7 天內決定訂閱 Ubuntu Pro，或先限制對外連線 |
| 訂閱 Pro | 使用者用文字給了明確的升級、淘汰或訂閱日期（選項「計畫半年內升級 LTS」「計畫一年以上才升級」不算明確日期） | 可在指定期限內處理 | 〔日期〕前（前提：〔使用者說的內容〕；到期前重新健檢） |
| 訂閱 Pro | 隔離 | 需排程處理 | 30 天內決定 |

| 其他設定 | 嚴重度不是「高」，其他 | 需排程處理 | 下一個維護窗口（最長 30 天） |
| 稽核、其他 | 可達性或重要性為「不確定」或未回答 | 需補問後判定 | 30 天內決定 |
| 稽核、其他 | 其他 | 需排程處理 | 30 天內決定 |

## 第 3 輪：定稿交付（給高階主管）

第 3 輪的讀者是**不懂技術的高階主管**。回覆分三部分，順序固定：(1) 對話裡的主管報告（下方範本）；(2) 附錄：給系統維護廠商的處理追蹤表；(3) 用 `report-template.html` 產生的報告檔，讓使用者下載、列印成 PDF。

### 第 3 輪的寫法規則

- **主管報告（範本的一到七節）不談技術**：不寫公告編號（USN）、CVSS 分數、套件名稱、指令、OVAL、ESM 等字。改用下表的說法。只有「附錄」可以保留技術內容。

| 技術說法 | 主管報告的寫法 |
|---|---|
| 安全公告、重大／高風險公告 | 安全問題、嚴重的安全問題 |
| 免費修補未套用 | 有免費的安全更新還沒安裝 |
| 需要 Pro 才能取得的修補、ESM | 要訂閱 Ubuntu Pro 才拿得到的安全更新 |
| 自動更新沒有實際安裝修補 | 自動更新沒有真正把更新裝上 |
| 下一個維護窗口（最長 30 天） | 30 天內 |
| 需排程處理、需補問後判定等結論狀態 | 不寫結論狀態，只寫要做的事與期限 |
| 核心、重開機 | 重新啟動主機讓更新生效 |
| 已過標準維護期 | 作業系統已過免費維護期 |
| 網路途徑、入口公告 | 可以從網路被利用 |
| 暴露高／一般／隔離 | 對外或存放重要資料／內部使用／隔離環境 |
| ufw 未啟用 | 主機本身的防火牆沒有開 |
| USG、CIS／DISA-STIG | 設定基準的稽核工具 |

- **資料來源**：有第 2 輪時，依第 2 輪的處理清單（第 1 輪的列套用第 2 輪的變更）；沒有第 2 輪時，依第 1 輪的處理清單，情境一律寫「未提供」。
- **各主機的風險**：這台主機有任何「需立即處理」的列、有「網路」或「相鄰網路」途徑的重大或高風險公告，或 `support_status` 為 esm、legacy、eol、nonlts → 高；不是高，但處理清單裡有這台主機的列 → 中；沒有任何列 → 低。
- **各主機要做的事**：取這台主機期限最短的項目，最多兩項，依 P 編號順序，用「；」連接，改寫成主管能懂的說法；期限寫最短的那一個。沒有任何項目時寫「目前沒有需要處理的事項」，期限寫「—」。
- **處理時程**：每個項目依期限放進一格。「7 天內」放期限是「7 天內」或「7 天內決定…」的項目；期限是「網路途徑的重大與高風險公告 7 天內；其餘下一個維護窗口（最長 30 天）」的免費修補，拆成兩條：「〔主機〕先修可以從網路被利用的問題」放 7 天內、「〔主機〕裝完其餘免費更新」放 30 天內；期限以「30 天內決定」開頭的項目只放 30 天內（寫成「決定……」）；「〔日期〕前」的項目放 30 天內，並把日期寫進文字。「之後每月」固定放「每月重新健檢一次」。同一件事、多台主機合成一條，例如「H02、H03 安裝安全更新」。
- **第一節的三點**：第 1 點寫期限最短、類型為免費修補或訂閱 Pro 的項目（沒有時寫處理清單第一列）；第 2 點寫類型為自動更新的項目（沒有時寫處理清單裡下一個不同的項目）；第 3 點照範本。
- **請您決定的事**：固定三列，依序為「核准修補作業」「主機維護方式」「重新健檢」。沒有 A 類時，第二列改寫成「主機維護方式：本次不需要採購」，需要預算寫「不需要」。

### 產生報告檔

1. 用程式讀取 `report-template.html`（專案檔案或對話中上傳的檔案）。
2. 只把 `<script type="application/json" id="report-data">` 裡的 JSON 換成這一輪的報告資料（格式見下方），其餘內容一個字都不改。
3. 存成 `主機資安健檢主管報告-〔basis_month〕.html`，提供下載連結。
4. 不能執行程式、或讀不到 `report-template.html` 時，**不要自己重寫 HTML**。改在「下載主管報告」那一節輸出報告資料（`json` 程式碼區塊），並寫固定句：「請用瀏覽器開啟 skill 資料夾裡的 report-template.html，按『載入報告資料』，把上面這段資料整段貼上，再按『顯示報告』。」

**報告資料的格式**（欄位名稱與型別不可更改；所有文字都要用主管報告的寫法，不談技術）：

```json
{
  "title": "主機資安健檢：主管報告",
  "date": "〔basis_month〕",
  "host_count": 〔主機數，數字〕,
  "overall": "〔高、中或低〕",
  "overall_reason": "〔第一節的一句原因〕",
  "summary": ["〔第一節第 1 點〕", "〔第 2 點〕", "〔第 3 點〕"],
  "decisions": [
    {"item": "核准修補作業", "recommendation": "〔〕", "deadline": "〔〕", "owner": "機關資訊單位", "budget": false},
    {"item": "主機維護方式", "recommendation": "〔〕", "deadline": "〔〕", "owner": "機關資訊單位", "budget": 〔有 A 類寫 true，否則 false〕},
    {"item": "重新健檢", "recommendation": "修補完成後立即重新健檢，之後每月一次", "deadline": "修補完成後", "owner": "系統維護廠商", "budget": false}
  ],
  "hosts": [
    {"tag": "〔tag〕", "role": "〔第三節的用途〕", "exposure": "〔暴露高、一般、隔離，或空字串〕", "risk": "〔高、中或低〕",

     "action": "〔第三節要做的事〕", "deadline": "〔第三節的期限〕"}
  ],
```

`budget`、`needed` 只能寫 true 或 false，不加引號；不要放 `sample` 欄位。字串裡不要用半形雙引號（"）和小於號（<），要引用時用全形「」。報告資料裡的數字只有 `pro_needed`、`free_pending`、`host_count` 三種，照抄欄位；範本會依這些數字畫各主機的長條圖，不要自己計算或加總。`exposure` 用判定時的原詞（暴露高、一般、隔離），範本會自動換成主管看得懂的說法。
